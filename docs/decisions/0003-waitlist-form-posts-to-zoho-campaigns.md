# 0003. The waitlist runs its own double opt-in

Status: proposed (Claude, 2026-11-23). Accepted when Santiago merges the branch.

## Context

The first version let Zoho Campaigns own the double opt-in. Its confirmation email is one org-wide message for both languages, sends people to a Zoho page, and already lands in spam, with no room to change the HTML. Santiago chose to confirm with our own email instead (2026-11-23). The alternatives were Zoho confirming and Amazon SES. SES needs a new AWS account and a sandbox review. Resend's free plan caps at 100 emails a day, which a launch day could exceed.

## Decision

- **Flow.** Signup never calls Zoho. The server action validates, throttles, seals a token and emails a confirm link through Zoho CPaaS. Zoho Campaigns is called only after the person confirms. The form gives the same answer for a new address and a known one.
- **Token.** AES-256-GCM, so the URL carries no readable personal data. The purpose is bound as additional data, so a token sealed for another purpose cannot be replayed as a confirmation. It lasts 7 days. `WAITLIST_TOKEN_KEY` is 32 random bytes in base64, and `WAITLIST_TOKEN_KEY_PREVIOUS` is optional, so rotating the key does not break links already sent. The throttle and confirm-guard hash key derives from it with HKDF. The cached Zoho access token is sealed with the token key itself under its own purpose, `zoho-access-token`, bound as additional data, so neither kind of token opens as the other. The spec called for an HKDF-derived key at rest there; the purpose binding is what was built. Either way there are no extra secrets. The payload carries the policy version the person saw, and the Zoho `source` records it.
- **Confirm page.** `/confirm` (es `/confirmar`) is a Server Component. Opening the link changes nothing, because corporate link scanners open every link. A button posts to `confirmWaitlist`, which subscribes and redirects to `/confirmed`, so reloading does not resubscribe. The page is noindex with `referrer: no-referrer`. The token's locale picks the Zoho list. When a live deploy's configuration is broken, a link reads as unavailable, never as invalid. An expired, invalid or unavailable answer to the button offers the way back to sign up again.
- **Locale.** The signup locale comes from a hidden form field, because `getLocale()` throws in Server Actions under next/root-params. It is accepted only for a locale that has all three of `ConfirmEmail`, `Confirm` and `Confirmed` (`signupLocales`), so a partial translation never mails raw message keys.
- **Ports and adapters.** All in `src/modules/waitlist`. `mailer.ts` and `audience.ts` are ports that return result unions and never throw across the boundary. `store.ts` is a port that can reject: Blobs errors, and its own 2-second timeout per operation. Its callers treat a store failure as a cache miss (the Zoho token cache) or as unavailable (the throttles and the confirm guard). Adapters: `mailer-cpaas`, `audience-zoho` (OAuth refresh, then `listsubscribe`), Netlify Blobs or memory for the store, and in-memory fakes. Only `server.ts` reads `process.env`: it validates the configuration once and builds the use cases. Every other file takes its settings as arguments, so node:test imports it without `server-only`.
- **Switching provider.** `server.ts` has two adapter maps. `mailers` is selected by `MAIL_PROVIDER` (`cpaas`), and `audiences` by `AUDIENCE_PROVIDER` (`zoho`, the default when unset). Each entry reads its own variables. An audience entry then builds on the shared store and token keys, which the Zoho adapter needs for its sealed token cache. To switch, add `mailer-<name>.ts` or `audience-<name>.ts`, add one entry to its map, set the provider variable and the adapter's own variables in Netlify, and delete the old adapter. An unknown provider value is invalid configuration: it fails closed and the log names the variable. Nothing else changes.
- **Zoho Campaigns.** An auth failure is HTTP 401 or a body code of 401 or 1007, with one refresh and one retry. The access token is cached sealed in Blobs. Refreshes are single-flight, and an instance adopts a token another one renewed, which keeps cold-start bursts under Zoho's refresh limit.
- **Throttles.** Per address, two consecutive gap slots and then day claims 1 to 3 are atomic create-only claims in Netlify Blobs, so concurrent requests cannot both pass: at most 1 email per 2 minutes and 3 per UTC day. The per-IP limit (30 an hour, loose on purpose for shared mobile and event Wi-Fi) and the daily total (`WAITLIST_DAILY_CAP`, default 1,000) are approximate. In live mode a request with no IP header goes into one shared bucket, `unknown`, and the instance logs `waitlist:ip-missing` once. The address is canonicalized for the hash only: a `+tag` is dropped for every domain, and Gmail also drops dots and maps googlemail.com to gmail.com. The email goes to the address as typed. IPv6 addresses count per /64; IPv4 per address. Over a limit the form says "check your inbox" per address, and "could not send" for IP and total, logged as `waitlist:throttle-refused` with the reason `ip` or `cap`. A send that fails gives back its two gap claims, so an immediate retry sends. It keeps its day claim: a timeout or a 5xx may still have delivered the email, so every attempt counts toward the 3 a day. The store holds only HMAC hashes and counters.
- **Per-address daily limit is per UTC day.** It is not a rolling 24 hours, because atomic create-only claims need fixed buckets. The 2-minute gap still holds across midnight, so one address can get at most 6 emails within about 15 minutes, once, around midnight UTC (7 pm in Colombia).
- **Confirm replay.** Every confirm would call Zoho's `listsubscribe`, which Zoho locks for 30 minutes after 500 calls a minute. A token that confirmed leaves a marker, `confirmed:<hmac>`, and a replay answers subscribed without calling Zoho. Any token gets one try a minute, `confirm:<hmac>:<minute>`. The HMAC is of the token's bytes, since base64url decoding accepts many spellings of one token. A new signup for the same address gets a new token and still reaches Zoho, so a person who unsubscribed can come back.
- **Deadlines.** `@netlify/blobs` sets no request timeout and retries a failed request 5 times, 5 seconds apart. Each Blobs operation is therefore cut at 2 seconds, and each use case at 20 seconds, which answers unavailable and logs `waitlist:deadline`. Netlify's synchronous Function limit is 60 seconds. Unexpected errors are logged by name only, never by message.
- **No typed text in the email.** The confirmation email goes to an unverified address, so it carries neither name nor address. Only the confirm page greets by name.
- **Origin tag (added 2026-11-24, parameter changed 2026-11-25).** A tracked link such as `/es?utm_source=instagram&utm_medium=bio#lista` names the channel that brought a signup. The action reads `utm_source` from the Referer, because a server action posts to the page's own URL, query included. It is the parameter the analytics tool reads, so one link names one origin in both. The analytics tool cannot tie a confirmation back to that channel (the e-mail link usually opens in another browser), so confirmations per channel come only from this tag. The first draft used `?o=`, which never shipped. Reading `searchParams` in the page would turn the prerendered home into a per-visit render. The tag is lowercased and kept only when it matches `^[a-z0-9-]{1,24}$`. It travels sealed in the token under the one-letter key `o`, left out when absent (at most 42 more characters in the link), and the Zoho `source` ends with ` · o=<tag>`. It is never logged. The tag is lost when the visitor leaves the home through a plain link and comes back without the query, and when a browser or extension strips the Referer. Either way the signup goes on without it. The privacy policy names it; the policy version is `2026-11-25-draft`.
- **Measurement and privacy text (2026-11-25).** The visit measurement and the origin tag ship with the interim policy version `2026-11-25-draft`; counsel review follows (owner decision). This replaces issue #14's criterion of a review before the merge. The Netlify variable `ANALYTICS_SCRIPT_SRC` turns the measurement off: unset it and rebuild.
- **The owner's answers to the questions meant for counsel (2026-11-25, relayed by him; counsel has not answered).** Visit measurement: the privacy policy informs people, and there is no consent banner. Whether prior authorization is needed (Law 1581, art. 9) stays open, and the production variable is the switch. International transfer: nothing more is done. His reasons: the countries are on the SIC's list of countries with adequate protection (not verified here against an official source; issue #14 could not read that list), and the policy says data may be stored outside Colombia. People already on the list: he says there are none yet (unverified; check Zoho before publishing).
- **Modes.** `fake` (in-memory mailer and audience, for local runs, e2e and previews) or `live`. A production build with anything but `WAITLIST_ADAPTER=live` fails in `next.config.ts`, and so does a deploy preview or branch deploy with `live` (any `CONTEXT` other than `production` or `dev`, which netlify dev sets), because a new Netlify variable reaches every deploy context by default. Invalid live configuration fails closed, and the log names the variables, never their values.
- **Unsubscribe.** Zoho adds the mandatory unsubscribe link to every newsletter and redirects to our static `/unsubscribed` (es `/baja`), which is noindex.
- **English is live.** Every piece of code handles `en`, both list keys are required, and the English namespaces are complete. `localeDetection` is `true` and the English URLs are in `lighthouserc.json`. English signups go to the «Newsletter» list.
- **Merge order.** Set the Netlify Production-context variables, including `WAITLIST_ADAPTER=live`, before merging. Until then production builds fail by design, and the last deploy stays up.
- **Not in v1.** Turnstile, until abuse shows up (Santiago approved). The daily cap is a circuit breaker, so an attacker can exhaust it and lock new signups out for the day. That tradeoff is accepted: it protects the domain's reputation.
- The waitlist form is still the exception to "every form returns a request number": our confirmation email is its receipt, and the list belongs to Fundación Embajadores de la Paz (OPTA). `apps/landing/AGENTS.md` says so.
- The Spanish copy is a draft with `[PENDIENTE]` markers. `npm run check:pending` checks every locale file and blocks publishing until they are gone.

## Open

All of these are live checks, to run with a throwaway address before relying on them.

- With both opt-in settings off (the lists' signup confirmation and the org-level double opt-in), `listsubscribe` adds the contact directly and Zoho sends nothing.
- What Zoho answers when the address is already on the list. Expected: code 0 with the fields updated.
- Whether `source` accepts the policy label, such as `rutaopta.org/es · policy 2026-11`.
- Whether Zoho's unsubscribe redirect is set per list or org-wide, and whether it can point at our page.
- Whether Netlify's Free plan keeps deploy-context values, so previews never see production secrets, and what Blobs costs at this volume.
- The "how do you want to take part" question needs custom fields in the Zoho lists. It is not in this version. The channel of origin rides in `source` instead (see Origin tag).
- Whether a `listsubscribe` for a contact already on the list updates its `source`, or keeps the first one.
- Counting by source: in Zoho Campaigns 3.0, Contact Source is an Advanced segmentation field (Professional plan). On the Standard plan, check whether a list export carries the source, so `o=<tag>` can be counted there.
